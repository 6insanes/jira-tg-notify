# jira-tg-notify

Уведомления о задачах Jira в Telegram без прав администратора Jira: поллер ходит в REST `/search` от твоего токена, сравнивает снимки задач и шлёт изменения в чат через Bot API.

Требования: Python 3.11+ и ничего кроме стандартной библиотеки — внешних зависимостей нет.

## Что уведомляет

- `created` — новая задача;
- `status` — смена статуса;
- `assignee` — смена исполнителя;
- `priority` — смена приоритета;
- `comment` — новый комментарий (автор, выдержка текста, ссылка на комментарий).

Комментарии — самый шумный тип, отключаются удалением `"comment"` из `notify.events`.

Целые проекты и отдельных авторов комментариев можно заглушить — см. [чёрный список проектов](#чёрный-список-проектов).

## Установка

```sh
mkdir -p ~/.config/jira-tg-notify
cp config.example.toml ~/.config/jira-tg-notify/config.toml
chmod 600 ~/.config/jira-tg-notify/config.toml
```

1. Создать бота у [@BotFather](https://t.me/BotFather) (`/newbot`) и вписать токен в `[telegram].token`.
   Токен НЕЛЬЗЯ вставлять в чат, коммиты или логи — только в файл с правами `600`.
2. Добавить бота в нужный чат (для группы — с правом писать; для топика — вписать `message_thread_id`).
3. Написать в чат любое сообщение (или добавить бота) и получить `chat_id`:

```sh
./jira_tg_notify.py --discover     # печатает chat_id и название чата
```

4. Вписать `chat_id` в конфиг и проверить доставку:

```sh
./jira_tg_notify.py --test
```

Jira-токен берётся из `~/.netrc` для `jira.netrc_host` (как у `jira` CLI), либо из `JIRA_TOKEN`, либо из `jira.api_token`.

## Запуск

```sh
# один проход, без отправки — проверить, что запрос и состояние работают
./jira_tg_notify.py --once --dry-run --verbose

# один проход с отправкой
./jira_tg_notify.py --once

# постоянный цикл
./jira_tg_notify.py
```

Первый запуск по умолчанию только запоминает текущие задачи (`notify.seed = true`) — история не прилетает. Поставить `false`, если нужен разовый дамп окна.

### systemd (пользовательский сервис)

```sh
mkdir -p ~/.config/systemd/user
cp jira-tg-notify.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now jira-tg-notify.service
journalctl --user -u jira-tg-notify -f
```

## Комментарии

- Комментарии запрашиваются только по изменившимся задачам (`updated` изменился) — это +1 запрос на задачу, попавшую в окно, а не на весь проект.
- Берутся только новые относительно `comment_id` в состоянии; порядок — по id.
- `comment_chars` (по умолчанию 400) — длина выдержки, `comment_max_per_poll` (10) — сколько сообщений о комментариях отправить за один проход, остальные запоминаются без отправки.
- `authors_exclude = ["Интеграция Планфикс"]` — не уведомлять о комментариях этих авторов; сравнивается **display name** из Jira, а не логин (полезно, чтобы не дублировать зеркало Planfix).
- При первом появлении задачи в состоянии текущие комментарии только запоминаются (baseline), без спама историей.
- Wiki-разметка Jira (`h2.`, `[url|text]`, `{code}`, `*bold*`) чистится до читаемого текста.

## Чёрный список проектов

```toml
[notify]
projects_exclude = ["OPS", "SUPPORT"]
```

- В списке — ключи проектов, а не названия: задача `OPS-123` → `OPS`. Регистр не важен.
- Уведомления по этим проектам не отправляются: ни `created`, ни смены полей, ни комментарии (комментарии по ним даже не запрашиваются — экономия запросов).
- Состояние при этом обновляется, поэтому проект можно безопасно убрать из списка и вернуть обратно: история изменений и комментариев за время «молчания» не прилетит, придут только новые.
- Список работает поверх `notify.jql`: JQL не меняется. Если исключённый проект большой и его задачи зря тратят запросы, сузьте и сам JQL (`... AND project NOT IN (OPS)`) — но помните, что в JQL `AND` приоритетнее `OR`, и при JQL вида `project = A OR project = B` добавка `AND project NOT IN (...)` не сработает как ожидается.

## Состояние и дедупликация

`~/.local/state/jira-tg-notify/state.db` — SQLite-база со снимком задач (`updated`, статус, исполнитель, приоритет, заголовок, `comment_id`). Записи старше 30 дней вычищаются. Удаление базы = повторный seed без уведомлений.

При первом запуске версии 2.0 старый `state.json` импортируется в базу и переименовывается в `state.json.migrated` — повторных уведомлений не будет. Если нечитаемый JSON, он уходит в `state.json.invalid`, а работа начинается с пустого состояния. Явно задать путь можно через `notify.state_db`; старый ключ `notify.state_file` продолжает работать (суффикс меняется на `.db`).

## Структура кода

```text
jira_tg_notify.py            точка входа (её запускает systemd)
jira_tg_notify/
  config.py       TOML -> dataclasses, пути состояния
  jira.py         Jira REST: поиск по JQL, комментарии
  telegram.py     Bot API: отправка, ретрай 429, --discover, --test
  models.py       IssueSnapshot и работа с комментариями
  events.py       какие уведомления порождает изменение
  formatting.py   текст сообщений (HTML, чистка wiki-разметки)
  storage.py      SQLite-состояние и импорт старого JSON
  poller.py       цикл опроса
  cli.py          разбор аргументов
tests/test_notify.py
```

Зависимости передаются через конструкторы (`JiraClient(fetch=...)`, `Poller(jira=..., telegram=...)`), поэтому тесты не патчат глобальные функции. Полный прогон: `python3 -m unittest discover -s tests`.

## Ограничения Jira Server (проверено на 9.16.1)

| Параметр | Значение |
|---|---|
| Rate limit | нет: `429`/`X-RateLimit` не отдаются, троттлинга в Server по умолчанию нет |
| `maxResults` в `/search` | жёсткий предел 1000 на запрос (больше молча урезается), ходим страницами по 100 |
| `total` | не ограничен (видели 1963 в выборке) |
| Стоимость запроса | 100 задач с полями ≈ 32 КБ и 0.13 с |
| Индекс JQL | обновляется асинхронно (обычно секунды) — окно `updated >= -10m` при интервале 60 с перекрывает лаг |
| Гранулярность `updated` | 1 секунда — дедупликация по `key` + `updated` |
| Комментарии | 1 запрос `/issue/{key}/comment` на изменившуюся задачу (страница 100, `orderBy=-created`) |
| Bot API | 4096 символов на сообщение, `429` с `retry_after` — обрабатывается, троттлинг ~20 сообщений/мин в группу |

Практическая нагрузка: один запрос в минуту — ничто для инстанса, но `jql` лучше держать узким (проекты/статусы), а не «всё за месяц».
